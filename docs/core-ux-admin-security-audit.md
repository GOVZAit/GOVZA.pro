Рабочая ветка: `improve/core-ux-admin-security`. Карты и программа лояльности отложены.
Это исходные наблюдения, а не заключение о безопасности всего приложения.

## Проверенный путь посетителя

1. Каталог `https://www.govza.pro/`: доступны поиск, категории, фильтры, профили и действие «Описать задачу».
2. Открытие заявки без входа: вместо формы показано приглашение авторизоваться и большая пустая область. Посетитель не может сначала описать потребность.
3. Авторизация: телефон/email, пароль, переключение регистрации и восстановление пароля видимы. Отправка писем и полноценный вход в этом проходе не проверялись.
4. Переход на `/admin` без сессии приводит к авторизации. Работу внутренних экранов администратора в браузере проверить без подходящей сессии не удалось; ниже приведены отдельные наблюдения по исходникам.

Сохранены и просмотрены исходные снимки `01-catalog.jpg`, `02-guest-request.jpg`, `03-auth.jpg` в каталоге аудита рабочего окружения. Проверенный браузерный viewport — настольный; мобильная доступность, скринридер и управление только клавиатурой пока не проверены.

## Первая очередь

### P1 — достоверность стартового каталога

`server/storage.ts` содержит массив `mastersData` с заданными рейтингами, количеством отзывов, выполненных работ, фотографиями Unsplash и признаками верификации/онлайн. `MemStorage.getMasters()` объединяет эти стартовые записи с постоянными профилями. На проверенном экране стартовые профили выглядят как обычные действующие специалисты без обозначения примера.

Нужно явно обозначать демонстрационные записи и отделить их показатели от подтверждённых отзывов и проверки исполнителей. Сохранить идентификаторы и существующие связи, не удалять записи вслепую. Проверить также страницу профиля, карту, выдачу и фильтр «Проверенные».

### P1 — заявка начинается с барьера авторизации

`client/src/components/broadcast-modal.tsx` прерывает гостевой сценарий до ввода задачи. Целевое поведение: сначала описание и выбор услуги, затем вход перед отправкой; после входа восстановить черновик и предложить проверку данных. Автоматически заявку после входа не отправлять. Черновики разных аккаунтов не смешивать, адрес и контактные данные не сохранять бессрочно в общем локальном хранилище.

### P2 — развитие клиентской базы в админке

`AdminUsers` и `/api/admin/users` уже дают поиск, фильтр по роли и пагинацию. SQL использует параметры и ограниченный набор публичных полей. Это полезная существующая основа. В просмотренной реализации нет экспорта клиентской базы; фильтры компонента живут только в локальном React state.

Следующий шаг: сохраняемые фильтры, контролируемый экспорт с подтверждением состава и количества строк, журналом выгрузки, защитой от CSV-формул и повторной проверкой прав. Пароли, токены и внутренности сессий в экспорт не включать. Отдельно определить права операторов до добавления управления ролями и массовых изменений.

## Предварительный обзор защиты

Положительные свойства, подтверждённые исходниками:

- Вход регенерирует идентификатор сессии; текущая `sessionVersion` сверяется с пользователем.
- Производственная cookie использует `secure`, `httpOnly`, `sameSite: lax`; production требует `SESSION_SECRET`.
- Общий административный guard проверяет серверную роль и версию сессии, запрещает кеширование, требует HTTPS в production и проверяет источник изменяющих запросов с защитным заголовком.
- Сброс пароля использует случайный токен и хранит его SHA-256; для запроса восстановления есть ограничение частоты.

Открытые проверки: защита входа/регистрации от перебора, CSRF остальных изменяющих маршрутов, IDOR заявок и переписок, загрузка документов, SSRF импортера, права экспорта, конфигурация работающего reverse proxy. Отсутствие найденного механизма в нескольких просмотренных файлах не считается доказанной уязвимостью. Активные атаки на production не выполнялись.
